## 18.2 設計目標の再定義: Winny の何を超えるのか

「Winny 以上の匿名性」を測定可能にするため、Winny が実際に破られた経路を列挙し、
現行 AETHER の対応状況を評価する。

| # | Winny の破れ方 | AETHER 現状 | 本改訂での扱い |
|:--|:---|:---|:---|
| ① | **クラスタワードで興味を隣人に宣言**。検索効率のために自分の関心を近傍へ配る設計自体が漏洩源だった | **既に無い**。Hint は blind_tag による試行復号方式で、購読宣言が原理的に存在しない | 維持。ゾーン購読を導入しない根拠 (18.6.2) |
| ② | **キー（索引）に保持者アドレスが載る**。捜査側はノードを立ててキーを収集し突合した | 設計上は無いが、Hint に位置情報が無いため受信不能というバグとして現れている | 18.5 で「位置は導出、非伝送」として解決 |
| ③ | **キャッシュ暗号が実質破れていた**。RC4 の鍵が導出可能で、保持者が何を持つか第三者に証明できた | **解決済**。ChaCha20-Poly1305 + `mailbox_key = SHA256(random nonce)`。保持者は鍵を持たない | 維持。Winny との最大の差 |
| ④ | **中継段数が実質1〜2段**。直近の上流/下流がほぼ実体だった | **解決済**。3-Hop Onion + Inbound Tunnel。Winny には受信側の匿名化機構自体が無かった | 維持。ただし回路が1本しかない (18.8.3-a) |
| ⑤ | **一次放流者の特定**。新規キーの初出ノードを観測すれば発信源が割れる。検挙例の大半がこれ | **未対策** | 18.3-A + 18.4.3 + Dandelion で対処 |

①③④が既に手元にある構成上の優位を前提に、②⑤を潰すのが本改訂の主眼である。

## 18.3 Winny から継承すべき性質（新規追加）

Winny が正しく捉えていて現行 AETHER に欠けている性質。重要度順。

### A. 索引のソフトステート化 — 保持者による Hint 再放流 ★最重要

**Winny の性質**: キーは寿命を持ち再放流され続けることで生存する。
放流者が居なくなってもキャッシュ保持者がいる限りコンテンツは発見できる。

**現行の欠陥**: Hint は発信時に1回流れて終わり。`HintPacket.ttl` はホップ数であって
寿命ではなく、しかも `decrement_ttl()` はどこからも呼ばれていない。
**発信者が落ちるとコンテンツは Mailbox に存在するのに永久に発見不能になる。**

**実装形**: PUT ペイロードを 2 分割し、保持者が索引を再投入できるようにする。

```
PUT(mailbox_key, [hint_blob(不透明)] ‖ [body_blob(不透明)])

保持者は hint_blob を復号できない（キーワード/共有秘密由来の鍵で暗号化済み）が、
バイト列としてそのまま Gossip へ再投入することはできる。
```

**匿名性への効果（可用性より大きい）**:
Winny の主要検挙経路だった「新規キーの初出ノード = 一次放流者」は t=0 の一瞬しか
観測機会がない。再放流が始まると、以降 Hint を流しているのは
**コンテンツと無関係なランダムな保持者**である。
18.4.3 の時間分離と Dandelion++ Stem を重ねると初出点の情報量は著しく下がる。

**再放流タイミングは `mailbox_key` から決定論的に導出すること。**
K 個の保持者が同一時間窓で送出すれば SeenCache が同一ハッシュとして畳むため、
帯域コストが K 倍にならない。

### B. アクセス連動 TTL

**Winny の性質**: キャッシュは LRU で、人気のあるものが生き残り、
誰も取りに来ないものは自然に消える。

**現行の欠陥**: `config.message_ttl_hours = 168` は宣言のみで **参照0件**。
`mailbox/server.rs` に TTL のコードが一切ない。

**実装形**: `StorageBackend::cleanup()` を経過時間ではなく
**GET のたびに寿命が延びる**方式にする。

**匿名性への効果**: 誰も要求しないコンテンツが自動的に消えるということは、
押収時に発見できる母数が「実際に流通しているもの」だけに縮むということである。
保持者が意図せず抱え込む期間も短くなる。

### C. 取得者が自動的に保持者になる — ただし単独では危険

**Winny の性質**: ダウンロードすると自動的にキャッシュ保持者になる。
「落とす」と「配る」が分離していない。

**単独導入は匿名性を悪化させる**: 保持者集合 = 興味を持った者の集合になり、
押収したノードの保持内容がそのまま嗜好プロファイルになる。
Winny はここを「中継しただけのものもキャッシュに入る」で薄めていたが、
AETHER は Onion 中継が暗号化されているため中継物をキャッシュできず、
**その薄め効果が構造的に存在しない。**

**成立条件**: 18.5 の `mailbox_key` 近傍によるランダム割当と**必ずセットで**運用する。

```
自分のキャッシュ = {自分が取得したもの} ∪ {位置が自分に近いもの}
                    ↑興味と相関             ↑完全にランダム、興味と無相関
```

`mailbox_key = SHA256(random nonce)` なので後者は自分の意思と無関係に降ってくる。
両者は暗号学的に区別不能であり、「欲しくて取ったのか、割り当てられたのか」を
第三者が判定できない。**この点は Winny より強い**（Winny の「中継したもの」は
経路上にあったという事実が残るが、AETHER の割当は完全にランダム）。

**運用パラメータ**: 割当分がキャッシュの過半を占めるように K と容量を設定すること。

### D. 部分保持での供給

**Winny の性質**: ダウンロード途中のファイルも、持っている部分だけ供給できる。

**実装形**: Part 5.2 の Reed-Solomon 3+2 分割をそのまま使う。
`reed-solomon-erasure` は Cargo.toml に宣言済み・**参照0件**。
各シャードが独立した `mailbox_key` を持てば、シャード単位で保持・供給・複製が完結する。
5個中3個で復元できるため、Winny の「キャッシュが消えて落ちきらない」問題への耐性も得る。

さらに 18.5.4 により、RS 分割は **Sybil 耐性・検閲耐性の主力**にもなる。

### E. クラスタワードの「診断」だけを受け取る

クラスタワード自体は最大の漏洩源のため採用しない。
ただし Winny がそこまでして解こうとした問題
= **「索引の配布コストがネットワーク規模の律速になる」** という診断は正しく、
これが AETHER の設計制約を決める。

AETHER は索引と本体が完全に分離しているため、ブロードキャスト対象は Hint だけである
（Winny はキー転送と本体転送が同じ経路構造の上に乗っていた）。

```
Hint 約100バイト（フレーミング込み）
   100万件/日  →   100 MB/日  ≈   9 kbps
  1000万件/日  →   1.0 GB/日  ≈  93 kbps
```

1000万件/日は Winny 最盛期を超える規模だが、それでも常時 93 kbps。
**全員が全 Hint を受け取る Broadcast Veil は Winny 級の規模までは素直に成立する。**
ゾーン分割で匿名集合を削る必要は当面ない (18.6.2 の根拠)。

裏を返すと **Hint の1バイトは全ノード数倍される**ため、ここだけは削る価値がある
（18.7-⑥ の auth_tag 削除）。

## 18.4 二層モード: 私信 / 公開 （Part 11 への差分）

### 18.4.1 現行実装の限界

`mailbox/schrodinger.rs:44` は事前共有秘密を要求する。

```rust
let shared_secret = {
    let contacts = self.contacts.lock().unwrap();
    *contacts.get(to).ok_or(AetherError::Config("Contact not found".into()))?
};
```

**事前に共有秘密を持つ相手にしか送れない**＝連絡先ベースの私信モデルであり、
Winny 後継（まだ出会っていない不特定多数への配布）が成立しない。

### 18.4.2 鍵源だけを差し替える

Hint / Mailbox の機構はそのまま使い、**共有秘密の出所のみ2系統にする。**

```
私信モード:   K = SharedSecret          (X3DH で確立)
公開モード:   K = Argon2id("aether_pub_v1" ‖ keyword)
```

以降の処理は完全に同一。

```
hint_key    = HKDF(K, "aether_hint_v1")
blind_tag   = HMAC(K, hint_nonce)[0:4]
mailbox_key = SHA256(nonce)              ← ランダムのまま。K からは導出不能
```

**Hint 構造体・ワイヤフォーマットの変更は不要**（Part 11.3 のまま）。
`SchrodingerMailbox` に鍵解決の分岐を1つ足すだけで済む。

公開モードの鍵導出に SHA256 ではなく **Argon2id** を使うのは、
観測ノードによる辞書攻撃に実コストを課すため (18.8.1)。

### 18.4.3 索引と本体の分離による効果と限界

**限界（明示する）**: 公開モードでは**索引 (Hint) 側は完全なシュレーディンガー性を
維持できない。** キーワード空間は辞書攻撃可能であり、Gossip を観測するノードは
総当たりで「これは "○○" 宛ての Hint だ」と判定できる。
これは公開検索可能性と両立しない原理的トレードオフである。

**維持されるもの**: `mailbox_key` はランダム nonce の SHA256 であり
キーワードからは導出できない。Hint を復号して初めて nonce が得られる。したがって:

- **本体を保持するノード** → 何を持っているか原理的に不明。**Winny のキャッシュ問題が構造的に解決**
- **Hint を中継するノード** → 辞書攻撃で話題は分かるが、誰が出したか・誰が取ったかは Onion/Tunnel で不明

Winny では「保持者 = 内容判明 + IP 判明」だった。
ここが「内容不明 + IP不明」になるのが構造的な差である。

### 18.4.4 Burn-on-Read の条件分岐

`mailbox/server.rs::handle_get` の取得時削除を**私信モードに限定**する。
公開モードは削除せず、18.3-C により取得者が保持者になることで拡散する。

### 18.4.5 Hint 放流の時間分離（改訂）

> **訂正**: 初版は「本体 PUT → ランダム遅延（数分〜数十分） → Hint 放流」と
> モード無差別に記述していた。**根拠も値も不適切だったので全面的に書き直す。**

#### 何を守っているのか

Onion により Hint の初出点は**出口リレー**になるため、
Winny の「初出ノード = 一次放流者」(18.2-⑤) は**既に成立していない**。
時間分離が守っているのは別の相関である。

```
ガードが見るもの : 「この IP が時刻 T まで D 秒間アップロードしていた」
全ノードが見るもの: 「時刻 T+ε に Hint が現れた」
```

**Hint の出現時刻は Broadcast Veil で全員に見える。**
ε が小さく D が特徴的なら、出口リレーを取らなくても紐づく。

#### だから小さい送信には要らない

この相関は PUT が観測可能なエンベロープを作る場合にしか成立しない。
定常の Gossip 中継トラフィックより十分小さい送信は
**自分が常時流している雑音に沈む**。

```
定常中継 1Mbps = 125 KB/s → 埋もれる上限 約 1MB (8秒ぶん)
チャット1通 約10KB  → 中継 0.08秒ぶん。遅延不要
4GB ファイル        → 数時間ぶん。遅延が必要
```

**リアルタイムチャットに遅延は入らない。**

#### 遅延量の決め方

「数分〜数十分」のような根拠のない値ではなく、観測量から逆算する。

```
匿名集合から  : W ≥ 目標件数 / 観測 Hint レート
エンベロープから: W ≥ 10 × 送出所要時間
待てる上限    : patience = max(60秒, 2 × 送出所要時間)

W = min( max(上2つ), patience )
```

**観測 Hint レートは Broadcast Veil のおかげでローカルで直接測れる**
（全 Hint が自分に届くため）。他の設計では得られない性質である。

#### ブートストラップ期の扱い ★重要

素朴に実装すると **「網が小さいほど長く待つ」という完全に逆の挙動**になる。
観測レートが 0 なら必要窓は無限大に発散し、上限まで待たされる。

しかも**待っても匿名集合は生まれない**。
利益ゼロのコストを、最も離脱されやすい立ち上げ期に払わせることになり、
**網が育つ経路そのものを塞ぐ。**

したがって Adaptive モードでは、
**待って得られる匿名集合が測定可能な水準 (2件) に達しない場合は遅延しない。**

| モード | 用途 |
|:---|:---|
| `Disabled` | ネットワーク構築中。一切遅延しない |
| `Adaptive`（既定） | 待てる範囲で待ち、届かない分は `ReleaseStatus` で報告。**網が育つと自動的に効き始める** |
| `Strict` | 使用感より秘匿を優先。目標に届かなくても上限まで待つ |

実測値 (`mailbox/hint_release.rs`):

```
              空(0/s)   0.1/s    1/s    10/s
チャット10KB       0       0       0       0     ← 常に遅延なし
2MB               0      1m      1m     40s
100MB             0      7m      7m      7m
4GB               0    4.4h    4.4h    4.4h
```

**匿名性の強度が黙って変わるのが一番まずい**ため、
`ReleaseStatus` が「なぜその待ち時間になったか」「目標に届いているか」を返す。

#### 中継していないと何も埋もれない

`relay_throughput_bps = 0` なら noise floor も 0 になり、
どんな小さな送信も遅延対象になる。
**中継しないほど自分の送信が目立つ**という関係が式にそのまま出る。

#### 時間分離では解決しない問題

`RelayClient` は回路を1本しか持たないため、
**PUT と Hint が同じ出口リレーを通る**。
出口リレー X は「Mailbox への転送」と「Gossip への Hint 投入」を
両方観測でき、時間をずらしても紐づけられる。

**回路分離（PUT は回路A、Hint は回路B）の方が費用対効果が高い**
（レイテンシコストがゼロ）。18.12 の未決定事項として残す。

## 18.5 Mailbox の位置決定 （Part 6 を置換 / Kademlia 廃止）

### 18.5.1 現行実装の欠陥

- `HintPayload { nonce, message_id, timestamp }` に **Mailbox の位置情報が無い**
- `OnionCircuit::wrap_packet` は引数 `_final_destination` を使っておらず、
  最深層フラグ `0x00` で終端した結果 **出口Relay がそのまま Mailbox になる**
- `process_hint()` (`schrodinger.rs:132`) は
  `return Ok(Some(b"Decrypted Message Mock".to_vec()));` のモック

つまり **Hint を復号して mailbox_key を得るところまでは動くが、
そのキーをどこへ問い合わせればよいか誰も知らない。**
これがシュレーディンガーMailbox の未完成部分の本体である (Part 15 の最終項目)。

### 18.5.2 リング座標 + K最近接（クエリを発生させない）

Part 10.1 が捨てた旧設計の欠陥は `Mailbox Key = Hash(受信者ID)` だった。
シュレーディンガー方式のキーは**完全にランダム**なので、
そこから配置場所を決めても受信者情報は漏れない。

```
position = H(mailbox_key ‖ K)
targets  = リレーリスト中、position に最も近い K 個
```

**`K`（Hint の復号鍵）を混ぜるのが重要**である。
`position = H(mailbox_key)` だと誰でも計算でき、観測ノードが任意コンテンツの
保持者を完全に列挙できてしまう (18.8.1)。K を混ぜることで
**私信モードの保持者位置は原理的に計算不能**になる。追加コストはゼロ。

**Kademlia の反復 FIND_VALUE は行わない。** それをやると Part 10.1 が挙げた
「検索の可視性 = 誰が誰を探しているかが分かる」が再発する。代わりに:

- リレーの ring position は **NodeId から決定論的に導出**（広告不要）
- 各ノードは**リレーリストをローカル保持**（PEX で更新、18.6.1）
- K最近接は**ローカル計算のみ**。ネットワークへ問い合わせない

Tor の consensus に近い構成であり、**DHT を丸ごと捨てられる。**
Part 6.2 / 6.3（256 k-bucket、再帰 FIND_NODE、`core/src/dht/mod.rs` は現在 0 バイト）は
実装不要となる。

### 18.5.3 NodeId の Sybil 耐性 ★未解決だった重大欠陥

**NodeId を Ed25519 公開鍵からそのまま導出する案は破綻する。**
NodeId は自由に生成できるため、攻撃者は毎秒数百万個の鍵を生成し、
**狙った `mailbox_key` の隣に着地する NodeId を選べる。**

- 特定コンテンツの保持者に確実になれる
- リング上の連続した弧を占拠し、その範囲の全コンテンツを支配できる
- 特定ノードを取り囲んで eclipse できる

**対策1: NodeId 生成に PoW**

```
有効な NodeId の条件: Argon2id(pubkey) の先頭 D ビットがゼロ
```

**対策2: エポックビーコンで位置を固定させない**

```
position   = H(NodeId ‖ epoch_seed)
epoch_seed = 直近エポックの Gossip 由来のハッシュ（1日ごとに更新）
```

グラインドした位置が **1エポックしか持たない**。
Tor が hsdir 配置に shared random value を使うのと同じ発想。

代償としてエポックごとに担当が移動するが、
**18.3-A（再放流）と 18.3-B（アクセス連動TTL）がそのまま移行機構になる。**
人気があるものは移動先で再放流されて生き残り、誰も取らないものは移動せず消える。
副作用ではなく設計として噛み合っている。

### 18.5.4 シャードごとに独立した位置

```
shard_i の position = H(mailbox_key ‖ K ‖ i)
```

Reed-Solomon 3+2 のシャードがリング全体に散る。攻撃者が1つの弧を支配しても:

- 取れるシャードは1個 → **復元できない**
- 検閲するには 5個中3個をリング上の離れた位置で同時に押さえる必要がある

18.3-D の RS 分割が、可用性だけでなく **Sybil 耐性・検閲耐性の主力**となる。

## 18.8 脅威モデル別評価

### 18.8.1 観測ノード（Winny 捜査ノードと同型）

攻撃者が正規ノードとして参加し、自分に届くものを全て記録する。

| 得られる | 得られない |
|:---|:---|
| **全 Hint**（Broadcast Veil のため当然） | 私信モードの Hint の中身（共有秘密が無く blind_tag も無意味） |
| 公開モードの Hint の**キーワード**（辞書攻撃） | PUT の発信者（Onion 経由 → 出口Relay まで） |
| `mailbox_key`（Hint を復号できた場合） | GET の要求者（Inbound Tunnel 経由 → 最終ホップまで） |
| **そこから計算される保持者アドレス**（公開モードのみ、18.5.2 の K 混入後） | 保持されている本体の中身（保持者が鍵を持たない） |

**私信モードは強い。** blind_tag は共有秘密を持たない観測ノードには
4 バイトのランダム値にしか見えない。

**公開モードで守れるものの線引き**（索引と保持者の把握は避けられない）:

- **誰が出したか** → Onion + 時間分離 (18.4.5) + Dandelion
- **誰が取ったか** → Inbound Tunnel
- **保持が意図を意味しないこと** → ランダム割当 (18.3-C)
- **保持者が中身を読めないこと** → mailbox_key がランダム、鍵が無い

Winny は後2者が崩壊していた（キャッシュが復号可能、自分で選んで落としたものが入る）。
そこが構造的な差である。

### 18.8.2 Sybil / 位置グラインディング

18.5.3 参照。**現行案の最大の穴**であり、
NodeId PoW + エポックビーコン + シャード分散配置の3点で対処する。

### 18.8.3 トラフィック分析

**構造的に強い部分**: Hint の Gossip は全ノードが同量を送受信し、内容と無関係に一様。
**無料で手に入る良質なカバートラフィック**であり、自分の興味と相関しない。
Winny の匿名性の本質（全員が他人のために動くので通信量が自分の活動を意味しない）を
より強い形で継承している。

**弱い部分**:

**(a) 回路が1本しかなく、ローテーションも無い**

```rust
// net/relay.rs
entry_connection: Option<QuicConnection>,   // 1本
circuit: Option<OnionCircuit>,              // 1本
```

`set_circuit()` は「テスト用・デバッグ用」とドキュメントされており、
**回路構築ロジック自体が未実装**。
この構造では単一の入口Relay が全 PUT・全 GET・全 Hint 放流を観測する。

さらに **ガード方針が存在しない。** 毎回ランダムに入口を選ぶと、
攻撃者シェア f に対して「いつか敵の入口を引く」確率が時間とともに 1 に収束する。
Tor がガード（少数の固定入口）を採用したのはこの計算のため。**方針の決定が必要** (18.11)。

**(b) サイズが指紋になる**

本体 PUT が任意長の一塊であるため、出口Relay で観測した PUT のサイズと
どこかで観測した GET のサイズが一致すれば、暗号を破らずに紐づく。

**固定チャンクサイズ（64KB または 256KB、末尾パディング）への正規化が
最もコスト対効果の高いトラフィック分析対策。** RS シャードと自然に噛み合う。

**(c) 中継トラフィックと自分の発信が分離している**

`Router::send_packet` と `RelayClient::send_raw_packet` が別経路で送出タイミングが独立。
第一ホップの観測者が「中継」と「本人発」をタイミングで分離できる。→ 18.9

**(d) コネクションプールの再利用窓**

`net/connection_pool.rs` は同一アドレスへの QUIC 接続を TTL 60 秒で再利用する。
60秒間の全アクティビティが同一 QUIC 接続に乗るため、リンク可能性の窓になる。
用途別回路と併せて設計すべきパラメータ。

### 18.8.4 守れるもの / 守れないものの線引き

**情報理論的に守れる（統計的でない）**

- **受信者匿名性** — Broadcast Veil。全員が全 Hint を受け取るため、
  誰が使ったかは原理的に判定不能。**設計上ここが最も強く、ゾーンを導入しない理由**
- **保持内容の秘匿** — mailbox_key がランダム、鍵が保持者に無い

**確率的に守れる（攻撃者シェアに依存）**

- 送信者匿名性 — 3-Hop Onion。入口と出口を同時に押さえられると破れる
- 一次放流者 — 時間分離 + Dandelion + 再放流で情報量を下げるが、ゼロにはならない

**守れない（明示する）**

- **グローバル受動観測 (GPA)** — Tor も I2P も守れない。AETHER も守れない
- **公開モードの索引** — 公開検索可能性と交換不能
- 大容量転送の**総量相関** — 中継/保管の比率でしか薄められない。パラメータ問題

## 18.9 Traffic Shaping の再定義 （Part 3.5 への差分）

**4GB の転送は Zoom には見えない。** 大容量配布と VBR ビデオ模倣は元々両立しない。
`net/shaper.rs` は削除せず、目的を差し替える。

| | 転換前 (Part 3.5) | 転換後 |
|:---|:---|:---|
| 目標 | ビデオ通話に見せる | **自分が発信した通信と、他人のために中継した通信を外部から区別不能にする** |
| 手段 | `VbrStrategy`（Iフレーム/Pフレーム、Box-Muller） | 固定チャンクサイズへの正規化 + 中継/発信の送出キュー統合 |
| 優先度 | Phase 5 | Phase 3（下げる） |

Winny の本当の匿名性は「自分の通信量が自分の活動を意味しない」ことにあった。
既存の `TrafficShaper` は mpsc キューと送出間隔制御の骨格を持つため、
`VbrStrategy` を差し替えるだけで移行できる。

| **穴1: ガード方針** | ✅ | `net/guard.rs` 新設。標本3本・実使用1本、60日ローテーション、連続失敗3回で降格、稼働実績による重み付け抽選。**永続化を必須化**し、破損ファイルは黙って空集合に戻さずエラーにする（黙って戻すと「起動のたびに再抽選」＝ランダム選択に退化し、ガード方式の意味が消えるため）。`RelayClient::connect_guard()` から利用 |
| ConnectionPool のホットパス | ✅ | `get_connection` のたびに全走査 + 書き込みロックしていたのを 5秒間隔に償却。送信の直列化を解消 |
| Mailbox のホットパス | ✅ | `ensure_capacity` が PUT のたびに `size_on_disk()`（ディレクトリ stat）を呼んでいたのを 30秒キャッシュ化。上限の8割を超えたら毎回測り直す |

**重要な副次的発見**: 重複排除ハッシュは **TTL を除外する必要がある**。
従来の `calculate_hash` はパケット全体を serialize していたため、
Phase 0-③ で TTL を減らし始めると同一 Hint が別物と判定され、
**重複排除が完全に無効化されて Gossip が無限ループする**ところだった。
`HintPacket::id()` は version / blind_tag / nonce / ciphertext のみをハッシュする。
回帰防止テストを `protocol::hint` と `net::gossip` の両方に置いてある。

`cargo test` 88件パス / `cargo clippy` 警告0。E2E: `core/tests/e2e_schrodinger.rs`

|:---|:---|:---|
| **リング座標** | ✅ | `net/ring.rs`。`position = H(mailbox_key ‖ K)`。K を混ぜないと観測ノードが任意コンテンツの保持者を列挙できる。`epoch_seed` は固定値のスロットのみ確保（Phase 3 で外部ビーコンに差し替え。NodeId 形式は変えずに済む） |
| **リレーリスト** | ✅ | `net/relay_list.rs`。`insert` は NodeId PoW を検証してから登録。K最近接は**問い合わせゼロ**で、Part 10.1 の「検索の可視性」が原理的に発生しない。**Kademlia (Part 6.2/6.3) は不要になった** |
| **PoW** | ✅ | `crypto/pow.rs`。Hint = SHA-256（全件検証されるため）、NodeId = Argon2id（登録時のみ、ASIC 優位を潰す）。18.11 の分析どおり |
| **Reed-Solomon 3+2** | ✅ | `mailbox/sharding.rs`。C(5,3)=10通り全ての組み合わせで復元することを検証。シャードごとに `H(mailbox_key ‖ K ‖ i)` の独立座標へ配置 (18.5.4) |
| **GET の返信経路** | ✅ | `MailboxGet` に返信先 `TunnelEndpoint` を同梱。Mailbox は Inbound Tunnel へ投げ返す。**要求者の IP を知らないまま応答する** |
| **`process_hint` のモック除去** | ✅ | 全シャードを並列要求 → トンネルで回収 → `reassemble` で復元。3個揃えば復元できるので遅いノードを待たない |
| `TypedForward (0x22)` | ✅ | MailboxGet を送信元を隠したまま Mailbox へ届ける |

**設計上の判断**:
- **Mailbox は「無い」を返さない。** 不在応答自体が、要求されたキーの不在を第三者に晒すため。
- **`process_hint` は同期的に中身を返さない。** 直接返させると要求者の IP が Mailbox に割れる。非同期性は仕様。
- **「どの1台も全シャードを持たない」は網の規模に依存する確率的性質**であり、候補が K 程度しかいない小さな網では保証できない。運用時は候補数 ≫ K を維持すること。

## 18.11 PoW のハッシュ関数選択（訂正）

> **訂正**: 本文書の初版 18.6.1 は「PoW は Argon2id を使い、パラメータは
> Part 6.6 の `t=3, m=64MB, p=4` 側へ寄せる」と記述していた。**これは誤りである。**
> Part 6.6 のそれは KeyStore の鍵導出（アンロック時に1回だけ実行）用であり、
> Hint の PoW に流用すると成立しない。実測 (`core/tests/pow_cost.rs`) に基づき訂正する。

### 18.11.1 支配的な関係式

攻撃者のコア数 M、ハッシュ1回のコスト C、難易度 D とすると:

```
攻撃者の生成レート = M / (2^D × C)   [件/秒]
各ノードの検証負荷 = 生成レート × C = M / 2^D   [コア]

飽和条件: M ≥ 2^D
```

**C が約分で消える。** つまり **フラッド耐性は難易度 D だけで決まり、
ハッシュ関数の重さとは無関係**である。

### 18.11.2 実測値

`cargo test --release --test pow_cost -- --ignored --nocapture`

```
1ハッシュ = 検証1回のコスト
  SHA-256              :      0.241 us
  Argon2id  1MB / t=1  :    276.033 us  (1146x)
  Argon2id 64MB / t=3  :  68060.079 us  (282592x)

同じ難易度で得られる耐性（飽和に必要な攻撃者コア数）
  difficulty 16 :    65536 コア  ← ハッシュ関数によらず同じ
  difficulty 22 :  4194304 コア

同じ難易度で正直な投稿者が払う生成時間
  difficulty 16 : SHA-256 0.02秒  /  Argon2 1MB   18.1秒
  difficulty 22 : SHA-256 1.01秒  /  Argon2 1MB 1157.8秒 (19分)
```

**メモリハード関数はこの脅威モデルで耐性を1ビットも増やさず、
正直な利用者のコストだけを1146倍にする。**

### 18.11.3 正しい構成

PoW は主役ではない。**ゴシップ網の本来の防御は暗号ではなく、隣人ごとのレート制限**である。

| 用途 | ハッシュ | 理由 |
|:---|:---|:---|
| **Hint の PoW** | **BLAKE3 / SHA-256** | 全ノードが全件検証するため、検証コストを限界まで削る |
| **NodeId の PoW** | **Argon2id（メモリハード）** | 検証は新規ピア登録時のみで頻度が低い。ASIC 優位を潰す価値がそのまま効く (18.5.3) |
| **KeyStore の KEK** | Argon2id `t=3, m=64MB, p=4` | Part 6.6 のまま。アンロック時に1回 |

**実際の負荷上限を決めるのはレート制限**である。

```
次数 d = 16、隣人1人あたり R = 20 件/秒 に制限
→ 受信レート上限 = 320 件/秒（攻撃者の資源によらず構造的に頭打ち）

  検証負荷 @ 320件/秒:
    SHA-256    : 0.008%  ← 無視できる
    Argon2 1MB : 88%     ← 1コアがほぼ埋まる
```

レート制限を入れると **攻撃者の制約が「ハッシュ能力」から「何本コネクションを張れるか」に変わる**。
SHA-256 に対する ASIC 優位（$2000 の Bitcoin ASIC ≒ CPU 2500万コア相当）も、
注入口がコネクション数で頭打ちになるため無効化される。
ASIC 対策は Hint PoW ではなく NodeId PoW の担当、という切り分けになる。
