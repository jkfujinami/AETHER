# Part 19: 未実装の棚卸し

Part 18 の設計に対して、コードに **何が入っていて何が入っていないか** を突き合わせた表。
「設計書に書いた」と「動く」の差分を明示するのが目的。

検証時点: 178 テスト通過 / clippy 警告 0 / CLI 実網往復確認済み（`aether send` + 受信）。

## 19.1 現在動くもの

`aether send` の実網往復を確認した経路が、そのまま「動く範囲」の定義になる。

```
tx: 種ノード参加 → リレー収束待ち → Onion 回路 → RS 5分割を独立座標へ配置
    → 放流方針判定（即時 / 遅延）→ Hint 放流
rx: 全 Hint をローカル購読 → blind_tag 照合 → mailbox_key 復号
    → Onion 経由で MailboxGet → Inbound Tunnel で受信 → 3シャード揃い次第復元
```

| 層 | 実装 |
|---|---|
| Onion 3-Hop / 出口分離 (`MailboxForward`, `TypedForward`) | ✅ |
| Inbound Tunnel（返信の送信元秘匿） | ✅ |
| Schrödinger Mailbox（保持者は中身も宛先も知らない） | ✅ |
| Broadcast Veil（全ノードが全 Hint を受信、判定は手元だけ） | ✅ |
| RS 3+2 シャーディング / 独立座標 `H(mailbox_key ‖ K ‖ i)` | ✅ |
| リング座標 + PEX（Kademlia 廃止） | ✅ |
| Guard（固定入口・60日ローテ・永続化） | ✅ |
| NAT 越え一式（PCP/NAT-PMP、EIM/EDM・EIF/Restricted 判定、punch、Connection Reversal） | ✅ |
| 世代式 Bloom SeenCache | ✅ |
| Hint バッチング（429→290 B/hint） | ✅ |
| 動的放流遅延（アップロード量ベース、ブートストラップ時は 0） | ✅ |
| NodeId PoW（Argon2id、Sybil 耐性） | ✅ |
| `aether init` / `id` / `start` / `send` | ✅ |

## 19.1.1 修正済み: 分割による認証の欠落（Part 11 → 18.5.4 の退行）

`aether send` の検証中に見つけて直した。**設計 Part 11 が持っていた性質が Part 18 で落ちていた。**

Part 11.3 の `MailboxEntry` は `auth_tag: [u8; 16]`（Poly1305）を持ち、
GET は本体まるごとを返す。この形なら悪意ある保持者がゴミを返しても
**AEAD がその場で落ちる**ので、次のレプリカを試せば済んでいた。

18.5.4 で Reed-Solomon 分割を入れた時点でこれが壊れた:

- AEAD タグは個々のシャードを守らない。**3枚合成した後にしか検証できない**
- RS は消失訂正符号であって誤り訂正符号ではない。
  「欠けている」は扱えるが「壊れている」は見分けられず、混ぜた時点で結果が丸ごと壊れる
- 復元失敗しても**どのシャードが原因か分からない**ため、除外して再試行もできない

結果: **K レプリカのうち1台が悪意を持つだけで、その本体の取得が永久に止まる。**
Sybil 保持者を明示的に脅威とする設計 (18.5.3) で、レプリカ数 K を増やすほど
「1台でも悪意がある確率」が上がる ── 冗長化が可用性を**下げる**という逆転が起きていた。

### 修正

シャードごとに封をする。保存形式:

```
[index(1)][original_len(4)][data][tag(16)]
tag = HMAC(HKDF(K, "aether_shard_mac_v1"), "aether_shard_mac_v1" ‖ mailbox_key ‖ body)[0..16]
```

- 保持者は共有秘密 K を持たないので**偽造できない**（index と長さは平文で見えているが、それだけでは形しか真似できない）
- タグが `mailbox_key` を含むので、**別メッセージのシャード混入も弾ける**（複数受信の同時進行で取り違えない）
- 検証は定数時間比較。バイト単位で早期 return するとタグを1バイトずつ詰めるオラクルになる
- コスト: 16 バイト × 5 シャード = **+80 バイト/メッセージ**

`reassemble()` は `mailbox_key` を取るようになった（封の検証に必要）。

回帰テストは `core/tests/schrodinger_properties.rs`。
11.6 のセキュリティ特性表を、**成立してはいけないこと**の側から検証している:

| 検証 | 内容 |
|---|---|
| `the_holder_learns_neither_content_nor_recipient` | 保存バイト列に宛先・平文・共有秘密・mailbox_key が現れない |
| `colluding_holders_cannot_tell_they_hold_the_same_body` | 保持者同士が同一本体の断片だと気づけない |
| `a_stranger_cannot_recognise_the_hint` | 別の共有秘密では blind_tag 照合で落ちる |
| `two_sends_to_the_same_peer_are_unlinkable` | 同一宛先・同一本文の2回送信が結びつかない |
| `one_malicious_holder_cannot_block_retrieval` | 偽造断片が先着しても復元できる |
| `shards_of_a_different_message_are_rejected` | 別メッセージの断片が混ざらない |

## 19.1.2 未解決: Burn-on-Read が Winny 後継路線と矛盾する ★

`MailboxServer::handle_get` は取得したエントリを**削除する**（`core/src/mailbox/server.rs:85`）。
Part 11 の「シュレーディンガー Mailbox の定義に従い」という記述通りの実装で、
**1対1メッセンジャーとしては正しい**（読んだら消える = 押収時に残らない）。

Part 18 で公開コンテンツ共有へ舵を切った時点で、これが破綻している。

### 何が起きるか

**1. 最初の1人が全員のぶんを消す**

`process_hint` は 5 シャード × K=5 レプリカ = **25 箇所へ GET を撃つ**。
応答した保持者は全員 burn するので、**1回の取得でその本体が網から消滅する**。
2人目以降は Hint を受け取っても取得できない。

**2. 公開モードでは1リクエスト検閲になる**

公開モード (19.3.1) では `K = Argon2id(keyword)` を**キーワードを知る全員が持つ**。
つまり攻撃者も持つ。すると:

```
Hint を傍受 → K で復号 → nonce → mailbox_key = SHA256(nonce)
            → shard_key(mailbox_key, i) と位置 H(mailbox_key ‖ K ‖ i) を全部計算
            → GET を撃つだけで全レプリカが自ら削除する
```

18.5.4 は「検閲するにはリング上の離れた3箇所を**同時に押さえる**必要がある」と主張しているが、
burn-on-read があると**押さえる必要すらない。取りに行けば消える。**
分散配置による検閲耐性が丸ごと無効化されている。

**3. 未実装機能の前提と衝突する**

- 18.3-B アクセス連動 TTL =「参照されるほど寿命が延びる」── burn-on-read の正反対
- 18.3-C ダウンローダが保持者になる ── 消えた後では複製元が無い
- 18.3-A Hint 再放流 ── 再放流しても本体が無い

### 選択肢

| 案 | 内容 | 代償 |
|---|---|---|
| A. モード分岐 | 私信は burn、公開コンテンツは保持 | Hint に1ビット必要。「これは公開だ」と保持者に見える = 分類のメタデータが漏れる |
| B. 一律保持 + TTL | 常に残し、18.3-B のアクセス連動 TTL で寿命管理 | 押収時に保持者の手元へ残る。ただし保持者は中身を読めない（暗号化済み）ので実害は小さい |
| C. 読み出し回数上限 | N 回配ってから消す | N の選び方に根拠が無い。人気コンテンツほど早く消える倒錯が残る |

**B を推す。** burn-on-read が守っていたのは「保持者の手元に残らない」だが、
保持者はそもそも共有秘密を持たず**中身も宛先も読めない**（19.1.1 のテストで確認済み）。
押収されても復号できないものを消して得られる利益は小さく、
引き換えに検閲耐性と公開共有の両方を失っている。

A のモード分岐は、保持者に「公開か私信か」を教えることになる。
Broadcast Veil で全 Hint を一様に見せている設計と噛み合わない。

**【解決 → 19.7】** 公開層の設計で **no-burn が必須**になったため、案 B（一律 no-burn +
アクセス連動 TTL）で確定。content は既に分散（RS × K最近接）なので容量は担当ぶん × K / N に収まる
── 容量パニックだったのは hint（全員ブロードキャスト）の方で、それは 19.1.3 で別途分散解決済み。
content と hint は別オブジェクト。

## 19.1.3 オフライン受信の設計：分散 Hint backlog（設計確定・未実装）

問題②（[19 の図](https://claude.ai/code/artifact/e8212ee2-a2fe-462e-8ade-0ba480ea1577)参照）の解。
Hint は gossip で網を一度舐めて消えるので、その通過中にオフラインだった受信者は
自分宛ての Hint を永久に取り逃す。これを分散保持で塞ぐ。

### 却下した代替案

- **フィールド削り（ciphertext を捨て mailbox_key を公開）**：私信で「断片↔Hint リンク」が
  Sybil 保持者に見える劣化を飲むことになり、かつ容量は 3.9GB→1.5GB 止まり。却下。
- **連絡先ごとの受信箱ポーリング**：既知連絡先しか救えず、公開側に広げるとキーワードへの
  興味が保持者に漏れる（＝却下済みの Zone）。部分策どまり。

### 3つのコストを分けて考える

分散保持が効くのは **保持（ディスク）だけ**。混同しないこと。

| コスト | 分散保持の効果 |
|---|---|
| ① ライブ受信（Hint が流れてくる帯域） | **変わらない**。全員が全 Hint をライブで受ける（Broadcast Veil 維持） |
| ② 24h 保持（ディスク） | **これを潰す。** 全員 3.9GB → 各自 数MB |
| ③ オフライン明けの追いつき DL | **変わらない**。取りこぼした窓ぶんを丸ごと落として手元で選ぶ（Broadcast Veil の税金）。留守時間に比例する一時コスト |

### 配置設計

- **Hint は割らない。丸ごと K=5 複製。** tiny(26〜90B)なので RS 誤り訂正は符号ピッダが節約分を食う。
  本体＝RS 分割（大きい）、Hint＝丸ごと複製（小さい）。
- **位置 = `H(hint_id)` の K 最近接**（連続）。本体シャードの `k_nearest` をそのまま流用。
  - 連続配置は隣接ノードの相関障害に弱いが、**再複製が一瞬（tiny）** なので検知さえ速ければ保つ。
  - 相関障害まで潰すなら **K 独立座標 `H(hint_id ‖ j)`** への hardening があるが、
    保持者どうしが arc を跨いで reconcile するグループを組む必要があり実装が重い。**MVP は連続、独立座標は将来。**
- **保持者主導の差分同期（anti-entropy）で churn を吸収。publisher は関与しない**
  （送信者は送信後すぐオフラインでよい、が肝。Kademlia の発行者再発行は使えない）。
  - 参加：新ノードが arc に入る → 現保持者と差分同期 → arc の Hint を pull → replica 化（自動）
  - 離脱：新しく責任範囲に入ったノードが同期で pull → K に戻る（自動、**pull 型で push 増幅なし**）
  - ③の追いつき用 minisketch が、そのまま churn 対策を兼ねる。

### K=5 の根拠（churn 生存率）

再複製サイクル d≈1分（検知が律速、コピーは一瞬）、窓 W=24h=1440 サイクル、
1ノードが1分で抜ける確率 p。「K 人全員が1サイクル内に抜ける」≈ p^K、24h 期待喪失 ≈ 1440·p^K。

churny な p=5%（セッション中央値20分）で:

| K | 24h で消える確率 |
|---|---|
| 3 | 約18%（不可） |
| 4 | 約0.9%（際どい） |
| **5** | **約0.045%（合格）** |
| 6 | 約0.002% |

→ **K=5**（本体と同値）。Hint は安いので churn がひどければ 6〜8 に上げても保持コストはほぼ不変
（上げると同期帯域だけ増える）。**生存の律速は検知の速さ**。

### 決めたパラメータ

| 項目 | 値 | 備考 |
|---|---|---|
| 保持窓 W | 24h | backlog のみ。本体 TTL も 24h に揃える |
| ライブ dedup / relay freshness | 15分（据え置き） | **backlog 窓とは別物。** SeenCache を 24h に伸ばす必要はない |
| backlog-accept 窓 | 24h | 戻ってきたノードは 24h 前までの Hint を受理・照合・取得。**ただし live gossip へ再 relay しない** |
| K（複製数） | 5 | 上表 |
| 検知 | heartbeat 30s / dead 90s（3 miss） | 生存の律速ノブ |
| reconcile 周期 | トポロジ変化で即（10s デバウンス）＋ 60s 定期 backstop | サイドチャネル相乗り |
| minisketch 差分上限 | 256 | 超過（長時間留守）は Bloom+一括転送にフォールバック |

### 容量（1台あたり = 全Hint × K / N）

上限レート（24h で 2590万 Hint）、K=5、1行 150B:

| ノード数 | 1台の保持 |
|---|---|
| 今（全員が全部） | 3.9 GB |
| 1,000 | 約 19 MB |
| 10,000 | 約 2 MB |
| 100,000 | 約 0.2 MB |

**ノードが増えるほど1台の負担は減る**（今と真逆）。N<K のブートストラップ時は全員が全部持つが、
その時は総 Hint も少ないので問題にならない。

### 残るコスト・注意

- **③ 追いつき DL は消せない**：留守 10分→約33MB、1h→約200MB、24h フル→約4.7GB。
  短い切断は minisketch 差分で安い。長時間フル留守だけ高い。
- **狙い撃ち検閲**：攻撃者がライブで Hint を見て `H(hint_id)` の K 位置を Sybil 占拠しうる。
  K 冗長 + NodeId PoW + **ライブ配信は既に済んでいる**ので、効くのは「その間オフラインの受信者への
  遅延妨害」まで。本体シャードと同じ防御線。
- **Hint PoW（19.2.1）が前提**：溜めて配れる以上、タダの Hint spam が backlog を埋める。先に配線する。

### コードの落とし所

- `core/src/net/hint_log.rs` ── `hint_id` キーの窓つき分散ストア（`H(hint_id)` 責任判定、24h プルーニング）
- `net/ring.rs` の `k_nearest` と `ReplicationManager` 相当を流用
- wire に `HintDigest`(0x12) / `HintReq` を追加、差分は既存 `GossipHintBatch` で返す
- `try_decrypt_hint` の freshness を backlog 経路では W=24h に緩め、**再 relay しない**フラグを通す

## 19.2 未実装 — 匿名性に穴が開くもの

これらは「機能が足りない」ではなく **設計上の防御が効いていない**。

### 19.2.1 Hint PoW が配線されていない ★

`core/src/crypto/pow.rs` の `hint` モジュールは完成しテスト済みだが、**呼び出し側が存在しない**。
`HintPacket` に nonce フィールドが無く、検証も走らない。

つまり現状 **Hint の生成コストはゼロ**。Broadcast Veil は全ノードが全 Hint を受け取る設計なので、
安価な Hint 洪水はそのまま全ノードの帯域を焼く。単一ノードへの DoS ではなく網全体への DoS になる。

必要な変更:
- `HintPacket` に `pow_nonce: u64` を追加（ワイヤ +8 バイト、290→298 B/hint）
- `id()` の対象に nonce を含める（含めないと nonce 差し替えで dedup を回避される）
- `GossipServer::handle_hint_packet` の **seen 判定より前** に検証
- 難易度は SHA-256 前提。Argon2 は誤り（18.11 参照。飽和条件 `M ≥ 2^D` からハッシュ単価 C が消えるため、
  メモリ困難性は洪水耐性を 1 ビットも増やさず 1146 倍のコストだけ払う）

### 19.2.2 前方秘匿性が無い ★★

`SharedSecret` が静的。`core/src/storage/mod.rs` は **0 バイト**、`KeyStore` は存在しない。

脅威モデル（日本警察: 押収 → フォレンジック）に対して、これが一番大きい穴。
端末を押収された時点で、**過去の全通信が復号される**。Onion も Mailbox も
「通信中の観測」に対する防御なので、押収後の解析には何も効かない。

必要なもの:
- Double Ratchet 相当（メッセージごとに鍵を進め、使った鍵を消す）
- ディスク上の鍵の暗号化（パスフレーズ由来 KEK）
- 受信済み本文の TTL 付き自動削除

### 19.2.3 鍵合意（X3DH）が無い

`--secret` で事前共有秘密を hex 直打ちしている。別経路で安全に渡す必要があり、
その別経路が匿名性の実効的な上限になる。また 19.2.2 の前提でもある
（ratchet は合意した初期鍵から始まる）。

副作用として、受信時に「誰から」が名乗れない。CLI は
「どの共有秘密で開いたか」しか表示できない。

### 19.2.4 回路の多重化・ローテーションが無い

PUT と Hint 放流が **同じ出口リレー** を通っている（`send` は 1 リレーで両方の回路を張る）。
出口を取られると「本体を置いた者と Hint を流した者は同一」が確定する。
時間分離（18.4.5）を入れた意味が、経路の共有で相殺されている。

### 19.2.5 Dandelion++ Stem が無い

Hint は生成直後から全方位へ拡散する。最初に流したノードの近傍に監視ノードがいると、
到達時刻の差から発信源を推定できる。Stem フェーズ（数ホップ単経路で運んでから拡散）で
発信源と拡散開始点を切り離す必要がある。

## 19.3 未実装 — Winny 後継として足りないもの

匿名性の穴ではないが、**これが無いと「連絡先限定メッセンジャー」であって Winny の後継ではない**。

### 19.3.1 公開モード（キーワード由来鍵）★

鍵源を `Argon2id(keyword)` にすれば、キーワードを知る者全員が同じ `SharedSecret` に到達し、
事前の連絡先登録なしにコンテンツを発見できる。これが公開共有の入口。
`core/src` に `keyword` / `public_mode` の実装は **一切無い**。

### 19.3.2 保持者による Hint 再放流（18.3-A）★

18.3 で **最重要** と位置づけたが未着手。
現状、Hint の TTL が尽きたあと publisher がオフラインになると、
本体は Mailbox に残っているのに **誰も mailbox_key を知らない** = 永久に発見不能になる。

Winny が持っていた「一度流れたものは流れ続ける」性質が、今の実装には無い。

### 19.3.3 ダウンローダが保持者になる（18.3-C）

取得したノードが自動的にレプリカになる仕組み。無いと、
人気コンテンツでも初期 K=5 台から増えず、可用性が publisher の在線に依存し続ける。

### 19.3.4 アクセス連動 TTL（18.3-B）

参照されるほど寿命が延び、参照されなければ消える。無いと全コンテンツが一律 TTL で消え、
ストレージも一律に食う。

| 未使用依存 `zstd` / `pqcrypto-kyber` | Cargo.toml にあるが未参照 | ビルド時間だけ。将来使うなら残す、使わないなら削る |
| テストのポート固定 | ハードコード | 並列実行で衝突しうる |
| punch の実効性 | 未検証 | localhost では NAT が無く検証不能。実 NAT 環境での確認が必要 |

## 19.5 着手順の推奨

匿名性の穴 → Winny 後継性 → 小物、の順。

1. **Hint PoW 配線**（19.2.1）— 半日。既に完成した部品を繋ぐだけ。放置すると網全体が DoS で落ちる

4. **前方秘匿性 + KeyStore**（19.2.2）— 1〜2週。脅威モデル上は最重要だが、範囲が大きい

6. **X3DH**（19.2.3）— 前方秘匿性の前提として一緒にやる
7. Dandelion++、CHUNK_SIZE、ダウンローダ保持者化

## 19.7 公開層の設計：索引・掲示板・ファイル検索（設計確定・未実装）

19.3.1（公開モード）を具体化した設計討議の記録。**公開共有・掲示板・ファイル検索は同じ索引機構**で、
AETHER は3層に畳める。19.1.2（burn-on-read）をここで解決する。

### 3層アーキテクチャ

```
基盤層     : リング + Onion + content-addressed 分散ストレージ（チャンク/RS/封/no-burn/TTL）+ PoW
索引層(pull): keyword → H(Argon2id(keyword)) → 記述子のランク付き集合
             ├─ 掲示板       （記述子 = スレ）
             └─ ファイル検索  （記述子 = ファイル）  ← 同じ層
私信層(push): Schrödinger Mailbox + Broadcast Veil + 分散 Hint backlog(19.1.3)
```

板・ファイル検索・テキスト投稿は全部「索引層」の同じ機構。本体だけ content-addressed ストレージに置く。
web-lite の `BoardOrchestrator` / `ThreadRanker` / `ThreadDAGManager` が索引層の参照実装。

### 公開の脅威モデルは反転する

キーワードは誰でも計算できる＝**警察も `K_pub = Argon2id(keyword)` を持つ**。公開コンテンツは
読める・在り処も割れる・検閲を試せる（＝内容の秘匿は原理的に不可能。"公開"の定義）。だから守る対象が変わる:

| 守らない | 守る |
|---|---|
| 内容の秘匿（意図的に公開） | 発行者の匿名性（Onion） |
| | DL者の匿名性（Onion + Inbound Tunnel） |
| | 検閲耐性（分散配置 + 再シード） |

「警察が読めても、誰が上げ・誰が落としたか分からず、簡単には消せない」＝Winny の性質。

### 掲示板 = pull-via-onion（Broadcast Veil を使わない）★

私信は push（自分宛てが飛んでくる → Broadcast Veil で興味を隠す）。
掲示板は browse＝**pull**（板→スレ一覧→スレ）。Onion 越しに取りに行く。

- 板 = `boardKey = Argon2id(板名)`、スレ = `threadKey = HKDF(boardKey, thread_id)`
- 投稿 = `H(mailbox_key ‖ threadKey ‖ i)` にシャード、no-burn
- 板を開く = `H(boardKey)` の板インデックス（スレ一覧）を Onion で pull
- スレを開く = `H(threadKey)` の投稿群を Onion で pull、定期再取得で更新
- スレ順序 = DAG（親参照）+ 累積 PoW ランク、名乗りは tripcode（擬似匿名）

隠れる: 投稿者・読者（Onion）。公開: 板名・スレ識別子・人気（元々公開）。

**帰結（重要）**: 掲示板は broadcast hint を一切出さない → **分散 Hint backlog(19.1.3) は私信専用**でよくなり、
量が読める。公開が主役でも hint stream は膨らまない。

**Schrödinger は私信専用**: 掲示板は受信者が「全員」＝隠す相手がいないので Schrödinger 不要。
位置は `H(threadKey)` で堂々と決め、Onion で投稿者/読者だけ隠す。

### 索引層が掲示板とファイル検索を統一

- **板を開く** = `H(Argon2id("板名"))` の索引を pull
- **検索する** = `H(Argon2id("キーワード"))` の索引を pull ── **同じ操作**

索引は**記述子だけ**持つ（`{content_id, 名前, サイズ, PoW, trip署名}` 数十バイト）。
本体は別（content-addressed）。→ 検索は軽い、DL は選んだ時だけ。

### content-addressing でファイル共有

- `file_id = H(ファイル内容)` → 重複排除・完全性・swarm（同じ file_id を多数が保持 →
  複数ソース並列 DL、DL者が保持者になる 18.3-C）
- **`CHUNK_SIZE`（19.4 で未使用）はここで使う**：チャンクごとに RS 分割＋封＋content-address
- 保持者はチャンクを暗号化状態で持つ＝中身を知らない（Winny キャッシュの否認可能性）
- 検索はタグ一致のみ（全文検索は無い＝重い＋匿名性に穴）

### 永続化ループ（Winny の「消えない」）＝ 19.1.2 の解決

公開は **no-burn 必須**（burn を残すと警察が fetch で削除）。そして **content は既に分散**
（RS シャードが K 最近接に）＝「全員が全部持つ」ではない → no-burn + アクセス連動 TTL(18.3-B)
でも容量は担当ぶん × K / N に収まる。

自己調整ループ:
```
発行(PoW) → 索引で発見 → fetch → 復号・ランク
    ↑                          ↓
 hint/索引 再放流(18.3-A)  ← DL者が保持者(18.3-C)
 頻度 ∝ 保持者 ∝ 人気         replica が人気で増える
```
人気は延命・放置は decay。人気コンテンツは「再シードを上回る速度で殺す」必要があり潰しにくい。

### 索引ポイズニング対策

Winny/Share が苦しんだ最大の敵。多層で「割に合わなく」する（銀の弾は無い）:

- 登録に PoW（コスト）
- DL 後に `content_id` 検証（偽物は落とせるが1回無駄になる）
- **実 replica 数でランク**（人気ファイルは実際に多数が保持＝カウンタ偽装より難しい。
  Sybil 水増しは NodeId PoW でコスト化）
- tripcode 評判（信頼できる名乗りを優先 ← 加重は 19.8 の信頼層、保留）
- 人気キーワードの索引肥大（数百万件）は **ランク上位 N 件に打ち切り** or **索引自体を分割**（hint backlog と同発想）

### FU ボタン（削除でなく沈める）

コミュニティ健全化の投票。ただし2点で作り替える:

- **ハード削除は物理的に強制できない**（no-burn・再シード・content-addressed・保持者は自律）
  → FU は**ランク/努力シグナル**にしかなり得ない
- **削除にすべきでない**：匿名 PoW 投票は「1ハッシュ1票」＝計算力票。警察が一番計算力を持つ
  → 削除ボタン＝警察に検閲ツールを渡す

効果は2段（削除しない）:
1. 閾値超えでクライアントが**既定折りたたみ**（データは残る、閾値を下げれば見える）
2. 高閾値で保持者が**再複製の手を抜く** → access-TTL で自然に薄まる

**決定的な安全弁 = access-override**: 実際に DL されてる（需要がある）ものは access-TTL が延びて生き残る
→ FU で消えるのは「嫌われ、かつ誰も要らない」＝spam だけ。**需要があるものは警察の FU 連打でも消せない**。

- ratio 判定（`FU重み ÷ 支持`、支持＝自身PoW＋replica数＋DL/賛成）。人気を沈めるには人気に比例した FU が要る
- FU-PoW は重め（casual 荒らし対策。計算力票なので resourced な相手には効かない → 本命は access-override）
- 票 = `(entry_id, nonce)` に束ねた PoW、entry の K保持者に蓄積、`vote_id` で dedup、reconcile で拡散
  （索引と同じ土管、新規機構ゼロ）

## 19.8 保留：健全性・信頼層・bot 弾き（後付け）★保留中

FU の票や rank を「計算力票」から「人間/信頼票」に変えたい、という議論。**現時点では保留**、後で上乗せする。

### なぜ保留か

- **Google/Cloudflare の bot 対策は移植不可**：中央の信頼できる観測者 + fingerprint に依存。
  AETHER には中央が無いし、fingerprint は匿名性を壊す。
- **「人間か試す一発チャレンジ」は無力**：LLM が Turing test を通す。
- 効くのは **主観的 web-of-trust**（各自が自分の種から信頼を伝播、Sybil は attack-edge 数で頭打ち、
  計算力でなく社会コストで縛る）。**だが匿名ネットワークで「相手が attestation グラフを引いて rank を
  算出」するのは重く、漏れも出る** ── ここが保留の直接理由。
- rank は「提示せず相手が算出」なら改竄不能だが、その算出自体が匿名網では非現実的。

### 後で乗せる時の設計方針（メモ）

- **主観的信頼**（グローバル root を作らない、コミュニティ種ごとに propagate）
- **算出型 rank**（本人は名乗らない・相手が算出。粗バケット S〜F で指紋を出さない、正確値はワイヤに乗せない）
- **invite-tree + 説明責任**でブートストラップ（招いた相手の悪事が招待者の信頼に跳ね返る）
- **rank は上限（レート・票重み・spam誘発機能）を上げるだけ、基本の投稿・閲覧はゲートしない**
  （silencing 装置化を防ぐ）＋ access-override が最後の砦
- ハードゲートだけ ZK / 匿名 credential で「≥ B」証明（phase 2）
- **正直な限界**: proof-of-personhood は未解決。これは計算力 Sybil を社会コスト Sybil に変えるだけで、
  辛抱強い浸透（本物に vouch させる長期工作）は防げない。

### なぜ後付けで問題ないか

FU / rank を人間加重にするには信頼層が要る。だが **FU 自体は信頼層なしでも
access-override + PoW + ratio で最低限成立する**（bot 連打は計算力票のままだが、需要があるものは
消せないので致命傷にならない）。→ 信頼層は独立した上乗せレイヤーとして後から足せる。
